Compact Data Pipeline Plan
==========================

Goal
----
Scale to millions of League matches without using SQLite as a raw Riot JSON blob store.

Current measured state:
- `league_data_v2_joseph.db` has 662,952 matches and 6,629,520 participant-history rows.
- The SQLite file is 55.82 GiB.
- A 2,000-match sample averaged about 81.8 KB for `raw_match_json` and about 323 bytes for `ordered_match_json`.

Conclusion:
- Raw JSON dominates disk usage and repeated preprocessing time.
- The sustainable path is compact typed facts plus prepared training examples, not bigger raw caches.


Design
------
1. Parse each Riot API match response once.
2. Extract compact match and participant facts.
3. Discard full raw JSON after successful extraction.
4. Store compact facts in partitioned Parquet under `ml/save_data/lol_dataset_v1/`.
5. Keep SQLite only for small crawler state: queues, processed PUUIDs, seen match IDs, and manifests.
6. Build model-ready `training_examples` Parquet from compact facts in chronological order.
7. Train from prepared Parquet instead of rebuilding dense features from SQLite every run.


Compact Facts To Keep
---------------------
Match rows:
- match ID, platform, queue, patch, timestamps, UTC game date, duration, winner
- 10 role-ordered champion slots and champion IDs when available
- objective outcomes: dragons, barons, heralds, towers, inhibitors, first blood, first tower
- gold differential and basic auxiliary targets

Participant rows:
- match ID, PUUID, slot, side, team, role, champion, win
- K/D/A, vision, champion damage, healing, gold, CS
- duration-normalized rates such as DPM, GPM, CSPM, VSPM, HPM

Prepared training examples:
- label, champion IDs, region ID, auxiliary targets
- dense recent-history feature vector built using only prior matches


Data To Discard By Default
--------------------------
- full raw Riot match JSON
- timelines and event streams
- items, perks/runes, challenges, and incidental Riot fields
- any future feature source that is not explicitly added to the compact schema

If future experiments require discarded data, refetch a targeted sample or add an optional cold archive outside the default SSD path.


Implementation Status
---------------------
Implemented:
- compact extraction utilities in `ml.data.compact_records`
- PyArrow-backed compact shard writer scaffolding in `ml.data.compact_parquet`
- structured SQLite-to-compact migration command in `ml.data.migrate_sqlite_to_compact_parquet`
- model-ready training example preparation in `ml.data.prepare_training_examples`
- unified trainer option `--training-data-dir` for prepared compact Parquet
- storage mode and compact dataset root live in `config/scraper.json`
- ignore rules for generated compact datasets

Commands
--------
Small migration smoke test:

```bash
venv/Scripts/python.exe -m ml.data.migrate_sqlite_to_compact_parquet --output-dir ml/save_data/lol_dataset_v1_smoke --limit-matches 1000 --limit-participants 10000 --match-batch-rows 1000 --participant-batch-rows 10000
```

Full migration:

```bash
venv/Scripts/python.exe -m ml.data.migrate_sqlite_to_compact_parquet --output-dir ml/save_data/lol_dataset_v1 --max-workers 4
```

Prepare model-ready training examples:

```bash
venv/Scripts/python.exe -m ml.data.prepare_training_examples --dataset-dir ml/save_data/lol_dataset_v1 --overwrite --max-workers 3
```

Train from prepared Parquet:

```bash
venv/Scripts/python.exe -m ml.trainer.train --training-data-dir ml/save_data/lol_dataset_v1
```

Scraper storage config:

```json
"storage": {
  "mode": "compact",
  "compact_dataset_dir": "ml/save_data/lol_dataset_v1"
}
```


Expected Impact
---------------
Storage:
- current 663k games should move from about 56 GiB raw SQLite to low-single-digit GiB compact Parquet
- 6M games should be plausible on a consumer SSD
- 60M games may still require larger/cold storage, but should be hundreds of GiB rather than multiple TiB

Time:
- existing DB migration is a one-time job
- dense feature preparation becomes a resumable dataset build, not a repeated training startup cost
- model iteration should read prepared training examples directly
- migration can parallelize by rowid chunks, but it may remain SSD-bound
- training-example preparation parallelizes safely by platform because player histories do not cross platforms


Guardrails
----------
- Do not run long training jobs casually.
- Do not store generated Parquet datasets in git.
- Do not use post-game participant facts as model inputs for the same match; they are only history for future matches or auxiliary labels.
- Keep schema changes versioned and explicit.
